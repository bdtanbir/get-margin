# Everything we append landed wrong on browser-printed PDFs

Reported as a stray mark near the edited word in a downloaded file, while the editor showed the
edit correctly. The mark was the visible corner of a much larger problem.

## Reproduction

A single fixture would not show it — the repo's fixtures are generated by `pdf-lib`, which balances
its operators. Generating a page the way the reported document was made (Chromium, HTML → PDF) and
patching a line put the cover and its replacement text **190pt down the page**, at quarter size:

![the patch landing in the wrong place]

Rendered with a yellow cover and red text to locate it, the patch was nowhere near the line it
belonged to.

## Root cause

Chromium opens every page it prints with a transform at the **top level**, outside any `q`/`Q`:

```
.23999999 0 0 -.23999999 0 842.88 cm
q
  0 0 2483.3496 3512.5 re W* n
  q  3.125 0 0 3.125 0 0 cm  ... the page ...  Q
Q
```

The `cm` is never popped, so the CTM at the end of the page's content is a **quarter-scale Y-flip**.

A PDF viewer concatenates the `/Contents` array into one stream, so whatever the page leaves applied
applies to whatever is appended next. `appendContent` wrapped each fragment in `q`/`Q`, which saves
and restores *our* state — it cannot undo a transform the page pushed and never popped.

`content.ts` said as much, and dismissed it:

> The leading `q` protects the fragment's graphics state but not its current transformation matrix
> if the page left one pushed; MuPDF's own writers make the same assumption, and **every producer of
> well-formed PDF balances its operators.**

Chromium does not, and Chromium prints a large share of the PDFs anyone will open in this app.

## Scope

Not the text patch. **Every writer that appends content**: text, shapes, ink, images, links,
stamps, whiteout, signatures, form fields. On any browser-printed PDF, all of them were drawn
through the leftover transform — scaled, mirrored, and displaced.

It went unnoticed because everything else about those documents works. They open, render, extract
text, and export; only appended content is misplaced, and only on documents whose producer leaves a
transform applied.

## Fix

`appendContent` now brackets the page's existing content with `q` / `Q` of its own, so every
appended fragment starts from the page's initial CTM — which is what all the geometry in
`write/` is computed against. The original bytes are untouched; the brackets are separate streams
around them.

The opening bracket carries a marker key so a page is wrapped once however many objects are written
to it, rather than nesting one layer per object.

`prependContent` needed no change: its fragment runs *before* the page's content, where the CTM is
still the initial one.

## Why no test caught it

Every fixture in this repository is generated by `pdf-lib`, which balances its operators, so the
assumption held for every document the suite had ever seen. The new test builds the hostile case
explicitly — a page with a dangling `cm` — and asserts the ink lands at the requested coordinates.
Emptying the brackets turns it red.

# Addendum: the replacement sat at the wrong height

The transform fix put appended content on the right part of the page. A second defect put the
replacement text at the wrong height *within* the line, which is what remained visible as stray
marks around the edited word.

## Measured

Diffing an export against its original — red for ink the original had and the export covered, green
for ink the export added — showed the two strings on **different baselines**: the replacement rode
several points above the text it replaced, while every surrounding line stayed put.

## Root cause

The writer derived both the size and the baseline from the glyph box:

```ts
let size = o.fontSize > 0 ? o.fontSize : h * 0.8
... `1 0 0 1 ${x} ${y + h - size * ASCENT_RATIO} Tm`
```

Both are guesses:

- `h * 0.8` assumes a fixed relationship between a glyph box and a font size. The real ratio depends
  on the font's ascent and descent.
- `y + h - size * ASCENT_RATIO` derives a baseline from the box and a constant. How far a baseline
  sits above the bottom of its box is the font's descender, which varies.

The extraction knew both answers and threw them away: `LineRun` already carried `size`, and MuPDF's
`onChar` supplies the pen position — the actual baseline — which `buildQuadIndex` ignored as
`_origin`.

**Fix:** `LineRun` gains `baseline`, and the patch writer sits the replacement on the line's own
baseline at the line's own size, falling back to the old derivation only when the extraction reports
neither.

## A test that was asserting a coincidence

`uses an explicit size over the derived one` compared the two outputs' lengths **in bytes**. That
only ever passed because the derived baseline changed with the font size and produced
differently-long decimals. Sitting text on the real baseline makes that number identical for both
sizes, so the test failed while the feature worked. It now measures rendered ink height.
